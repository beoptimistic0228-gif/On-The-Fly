# 그때그때 빌드 오케스트레이터

그때그때 앱을 **설계 → 구현 → 통합 검증 → 최종 감사** 파이프라인으로 만든다. SSOT는 `그때그때_PRD_v1.0.md`. 스택은 **Flutter** 확정. 중간 산출물은 `_workspace/`, 코드는 `lib/`.

**실행 모드: 혼합**
| Phase | 실행 모드 | 이유 |
|---|---|---|
| 1 설계 | 지속형 에이전트 협업 | spec-architect와 platform-integrator가 실현성 역질의를 주고받아야 함 |
| 2 구현 | 지속형 에이전트 협업 | 인터페이스 전달·이슈 수정 요청이 반복됨 |
| 3 통합 검증 | 지속형(qa-verifier 재사용) | 구현 팀과 같은 맥락에서 최종 점검 |
| 4 최종 감사 | 서브에이전트 위임 | 구현 팀과 대화 없이 독립 판정만 받으면 됨 |

**모델:** 호출 시 `model`을 넘기지 않는다. 각 에이전트 정의의 `model:`을 따른다(final-auditor는 fable, 나머지는 opus).

**범위:** PRD F-01~F-13 + D5 편입분 F-14a'~d'(정리 루프 내 단건 삭제, 정본 `_workspace/06_architect_delete.md` §0). 중복정리·일괄 삭제는 여전히 금지.

## Phase 0: 컨텍스트 확인 (항상 먼저)
1. `_workspace/` 존재 여부와 요청 종류로 분기한다.
   | 상황 | 분기 |
   |---|---|
   | `_workspace/` 없음 | **초기 실행** (Phase 1부터) |
   | 있음 + 특정 화면/기능 수정 | **부분 재실행** (해당 에이전트만 Phase 2 → 3 → 4) |
   | 있음 + 코드 변경 없는 검증 요청("재감사", "릴리스 재판정") | **검증만** (Phase 3 → 4, 구현 생략) |
   | 있음 + 새 요구/방향 전환 | **새 실행** (`_workspace/`를 `_workspace_prev_{YYYYMMDD}/`로 옮긴 뒤 Phase 1) |
2. 현재 상태 파악을 위해 읽는다: PRD, `00_decisions.md`, 관련 `01_architect_*.md`, `06_architect_delete.md` §0(삭제 관련 작업 시), 최신 `03_qa_report.md`, `04_final_audit.md`의 릴리스 판정.

## Phase 1: 설계
1. 이름 있는 에이전트로 실행한다(한 메시지에 병렬):
   - `Agent(name: "architect", subagent_type: "spec-architect", ...)`
   - `Agent(name: "integrator", subagent_type: "platform-integrator", ...)` — 실현성 검토 역할로 지시
2. architect가 `flutter-app-design` 스킬로 산출물 작성 → `_workspace/01_architect_*.md` (기능 추가 설계는 `0N_architect_{기능}.md`).
3. integrator가 데이터 모델·미분류 규칙·플랫폼 API의 실현성을 검토하고, 문제는 `SendMessage({to: "architect"})`로 역질의한다.
4. **PRD에 답 없는 결정은 사용자 승인**을 받아 `00_decisions.md`에 확정한다. 설계안은 plan 형태로 사용자에게 제시.

## Phase 2: 구현
1. 이름 있는 에이전트로 실행한다(Phase 1 에이전트가 살아 있으면 `SendMessage`로 이어서 쓴다):
   - `integrator`(platform-integrator), `builder`(feature-builder), `qa`(qa-verifier)
2. 태스크는 `TaskCreate`로 의존순서대로 만든다. `TaskCreate`가 없는 환경이면 `01_architect_tasks.md`에 체크박스로 진행을 기록한다. **우선순위: 핵심 루프(F-01~F-06) → 온보딩(F-07) → 영상·건너뛰기(F-08, F-11) → 분석(F-12) → 광고·IAP(F-09, F-10).**
3. 데이터 흐름:
   - integrator가 core 서비스(사진·DB·알림·삭제) 구현 → 공개 인터페이스를 `02_integrator_notes.md`에 문서화 → `SendMessage({to: "builder"})`로 전달.
   - builder는 그 인터페이스에만 의존해 화면 구현.
   - **각 모듈 완성 즉시** qa가 `incremental-qa`로 경계면 검증 → 이슈는 담당자에게 `SendMessage`로 직접 요청.
4. 구현 종료 게이트: `flutter analyze` No issues, `flutter test` 전부 통과. 실패하면 Phase 3으로 넘어가지 않는다.

## Phase 3: 통합 검증
1. qa가 핵심 불변식(중복방지, 미분류 정확성, 광고 위치, 프라이버시, 삭제 DEL-1'~8)을 최종 점검 → `03_qa_report.md` 갱신(해결된 이슈는 닫고 신규만 추가).

## Phase 4: 최종 감사 (자동, 구현이 끝날 때마다)
**트리거:** Phase 2를 거친 모든 실행(초기, 부분 재실행, 새 실행)과 "검증만" 분기에서 Phase 3 직후 **사용자에게 묻지 않고 자동 실행**한다. `lib/`·`android/`·`ios/`·`pubspec.yaml` 변경이 없는 설계 전용 실행에서만 생략하고, 생략 사실을 보고에 적는다.

1. `Agent(subagent_type: "final-auditor", ...)` 한 번 호출. 프롬프트에 이번 실행에서 바뀐 범위(기능 ID, 변경 파일)를 넘겨 그 범위를 중점으로 보게 하되, 프라이버시 경로 점검은 매번 전체를 본다.
2. 출력 `_workspace/04_final_audit.md`를 덮어쓰지 말고 맨 위에 `## {YYYY-MM-DD} 감사 ({범위})` 절을 추가한다. 이전 판정은 기록으로 남긴다.
3. 판정에 따라:
   - **통과 / 조건부**: 조건을 보고에 그대로 옮기고 종료.
   - **보류**: 차단 항목을 `05_fix_directives.md`에 수정 지시로 추가 → Phase 2(해당 에이전트만) → Phase 3 → Phase 4를 **1회만** 다시 돈다. 두 번째도 보류면 멈추고 사용자에게 보고한다(무한 루프 방지).
4. 플랫폼 기기 부재(iOS 실기기 등)처럼 코드로 해소할 수 없는 보류 사유는 수정 루프에 넣지 않고 "외부 조건"으로 분리 보고한다.

## 종합 보고
남은 이슈, 미해결 결정, 최종 감사 판정과 조건, 헛돈 에이전트 처리 내역을 사용자에게 보고한다.

## 데이터 전달 프로토콜
- **태스크**(`TaskCreate`/`TaskUpdate`, 없으면 태스크 파일 체크박스): 진행·의존 관리.
- **파일**(`_workspace/{phase}_{agent}_{artifact}.md`): 설계 산출물·인터페이스 계약·QA 리포트·감사 결과. 중간 파일 보존(감사용).
- **메시지**(`SendMessage`): 인터페이스 전달, 역질의, 이슈 수정 요청.
- 코드는 `lib/`에 직접 작성(최종 산출물).

## 에러 핸들링
- **헛돈 에이전트(no-op) 감지 & 폴백** (중요): 에이전트가 **도구 사용 0회로 반환**하거나, 지시한 산출물 파일이 실제로 생성/수정되지 않았거나, 반환이 지시 무관한 자기참조·프롬프트 에코이면 → **작업 미수행으로 간주**한다. 반환 텍스트만 믿지 말고 **실제 파일 상태(존재/변경)로 검증**하라.
  1. 1차: 더 명확·구체적인 지시로 **1회 자동 재시도**("반드시 Edit/Write로 실제 파일을 수정하라, 말로만 끝내지 마라" 명시).
  2. 재시도도 no-op이면: 작업 범위가 좁고 명확하면 **오케스트레이터가 직접 수행**(파일 읽고 편집), 넓으면 태스크를 쪼개 재할당.
  3. 어느 경우든 무엇이 헛돌았고 어떻게 처리했는지 사용자 보고에 남긴다.
- 지속형 에이전트가 응답하지 않으면 `SendMessage`로 상태 확인 후 재지시. 그래도 실패하면 같은 `subagent_type`을 새 이름으로 실행하고 작업 맥락을 프롬프트로 넘긴다.
- 사용량 한도·인증 만료·권한 거부는 재시도하지 않는다. 부분 산출물을 직접 확인해 진행 범위를 기록하고 사용자에게 보고한다(한도면 풀리는 시각 포함).
- 에이전트 1회 재시도 후 재실패 → 해당 결과 없이 진행하되 보고서에 **누락 명시**.
- 플랫폼 API가 PRD 시나리오 미지원(예: Android 이동 제약) → 삭제·강행 금지, 우회안을 근거와 함께 사용자에게 올림.
- 설계·구현 상충 → 데이터 삭제 없이 출처 병기 후 사용자 판단 요청.

## 테스트 시나리오
- **정상 흐름**: 초기 실행 → 설계 산출·승인 → 구현(핵심 루프 우선, 인터페이스 계약대로) → 점진 QA 통과 → analyze/test 그린 → Phase 4 자동 감사 "조건부" → 조건 포함 종합 보고. 기대: 배정 자산이 재로드에서 제외, 광고는 완료 뒤 1회.
- **부분 재실행 흐름**: "삭제 버튼 문구만 고쳐줘" → Phase 0 부분 재실행 → builder만 수정 → qa 경계면 확인 → Phase 4 자동 감사(삭제 범위 중점) → 보고.
- **에러 흐름**: Phase 4가 "보류"(예: 프라이버시 경로 발견) → `05_fix_directives.md` 추가 → integrator 수정 → qa 재검증 → 재감사 1회 → 여전히 보류면 루프 중단 후 사용자 보고.
